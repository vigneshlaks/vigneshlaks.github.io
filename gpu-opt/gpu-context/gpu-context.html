Contextualizing GPU Programming

Introduction

The terms defined during the onset of the GPU programming journey are a bit dull. Instead of throwing term after term at you, we'll define the terms as they come up naturally during our breakneck history lesson of the heart of GPUs, Streaming Multiprocessors (SMs).

Much of the traditional machinery of these diagrams are thrown out. Our motivation for peering at the hardware is to continuously reinforce the core concepts by revisiting them in different ways. For a more comprehensive understanding, see the references.

Context

Up to 2006, the graphics card design separated tasks into hardware sections representing disjoint parts of the video rendering process. Nvidia engineers would have to guess how much of a GPU die to allocate to each section. This meant predicting what developers would create with software and in turn the demand placed on each section of the hardware.

This inflexibility alongside the guesswork lead to the overhaul of the design.

Streaming Multiprocessors replaced all these units and with its advent brought:

  • Cores - Basic processing units of the GPU.
  • Warps - groups of 32 threads.
  • Warp Scheduler - mechanism making requests amongst other things and implementing SIMT. More later.
  • Special function units (SFUs) are designed to handle complex calculations like sin, cos, etc. They won't be referenced in diagrams moving forward.
  • Register files are a specific thread's storage.

Contrasting CPUs, GPUs elect to improve computation speed and incur memory overhead, as a tradeoff. In other words, the bottleneck is usually moving information around more than it is working with that information. Cleverly, threads in need of memory make requests in parallel to greatly reduce the overhead, known as "saturating the memory bus".

Fermi, Kepler, Maxwell, Pascal - 2010 - 2016

In 2010, Moore's Law allowed the compression of more cores onto the same hardware. This allowed for 4x throughput moving from 4 cores to 16 cores.

Fermi SMs used dual warp schedulers, allowing us to request for data and "saturate" faster.

In 2012, Kepler prioritized energy efficiency. The speed of the core clocks is lowered (meaning less cycles are performed). Transistors became smaller once more, helping compensate. 4 warp schedulers keep our threads even busier.

In 2014, Maxwell kept energy efficiency the focus. In a dramatic turn of events, the number of cores were reduced and simplifying design became the focus primarily for energy savings.

In 2016, Pascal introduced even smaller transistors. More Gflops and more cores equals more throughput.

As we've seen (and continue to see), GPUs improved as these numbers got bigger alongside core density increasing. Intuitively, the faster you can cycle/iterate (clock frequency) and the more things are cycling (cores) the more computations you can perform.

Gflops (Giga floating-point operations per second) encapsulates this idea well.

Volta, Turing - 2017, 2018

Instruction Pointers within warps could now also be individually assigned leading to less issues in throughput.

Specialization emerged once more in the form of tensor cores, motivated by the increasing demands from ml workloads.

Ampere - 2020

  • Warp Scheduler - mechanism making requests amongst other things and implementing SIMT. More later.
  • Special function units (SFUs) are designed to handle complex calculations like sin, cos, etc. They won't be referenced in diagrams moving forward.
  • Register files are a specific thread's storage.

Ampere introduced third generation tensor cores with fine-grained structured sparsity support. TensorFloat-32 (TF32) enabled automatic acceleration without code changes. An emphasis was placed on the improved performance of sparse matrices and offers a nice bridge between deep learning and gpu programming concepts*.

In hardware terms, we iteratively send our information from CPU to GPU to be handled in parallel by our cores. In software terms, we allocate memory on our host and device, launch kernel instances to be run in parallel on our threads.

Multiple Blocks on SMs
Multiple blocks running on each SM

Each SM computes one kernel instance and if too many instances are launched information is placed in a queue.

Concreting Everything

kernel<<<gridDim, blockDim>>>(args) represents our simplest syntax for a kernel launch where gridDim represents the number of kernel instances referenced earlier and blockDim represents the number of blocks per kernel.

Kernel functions are written from the point of view of a thread as this is the action that will be handled by every thread. Within our kernel function we get access to a number of terms encapsulating where we are within our kernel grid.

    float *h_x, *d_x;        // h=host, d=device
    int   nblocks=2, nthreads=8, nsize=2*8;

    h_x = (float *)malloc(nsize*sizeof(float));
    cudaMalloc((void **)&d_x, nsize*sizeof(float));

    my_first_kernel<<<nblocks, nthreads>>>(d_x);

    cudaMemcpy(h_x, d_x, nsize*sizeof(float),
                cudaMemcpyDeviceToHost);

    for (int n=0; n<nsize; n++)
        printf(" n, x = %d %f \n", n, h_x[n]);

    cudaFree(d_x); free(h_x);
}
